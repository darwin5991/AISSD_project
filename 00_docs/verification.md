# RTL 검증 계획

> **2026-11-10 명세 개정:** MAC 입력·가중치 레지스터 1단을 추가해 데이터·valid 경로를 3단으로 변경했다. MAC·Control RTL과 검증환경 코드를 3단 명세에 맞게 수정했고 새 검증 데이터·헤더 5종을 생성했다. 생성기 내부 검사는 PASS했지만 새 RTL의 테스트·시뮬레이션·합성·배치배선은 아직 실행하지 않았다. [변경 범위와 일정](mac_input_pipeline.md)을 따른다. 기존 실행 기록은 이전 구조의 이력으로 보존한다.

이 문서는 TB·tester·데이터 헤더와 Python golden 생성기의 구성 및 검증 원칙을 기록한다. 하드웨어 구조·포트·수치 설정·파이프라인 일정은 [architecture.md](architecture.md)를 기준으로 한다. 아직 정하지 않은 실행 조건은 8절에 구분한다.

## 1. 검증 방식

- 모듈별로 TB, tester, 데이터 헤더를 한 세트로 구성한다.
- Python에서 테스트 입력과 기대 출력을 미리 계산하고 파일로 생성한다.
- Tester는 생성된 입력을 공급하고 기대값과 비교한다. RTL과 같은 연산을 다시 구현해 정답을 계산하지 않는다.
- 데이터 출력뿐 아니라 valid, 주소, enable, busy, done 등 해당 모듈의 모든 출력 포트를 검증 대상으로 둔다.
- 순차 출력과 조합 출력을 구분해 값과 변화 시점을 확인한다.
- 시점 판단은 명세를 따른다. 기준 모델은 명세에서 작성하고, DUT의 실제 출력을 기대값으로 사용하지 않는다.

참고한 deit_fpga의 단위 TB는 TB와 tester를 분리하고, tester에서 자동 생성된 `<module>_tb_data.vh`를 include한다. 참고 프로젝트의 Top TB는 tester 역할을 TB 내부에 포함하지만, AISSD에서는 Top도 TB와 tester를 분리하는 구성을 따른다.

## 2. 파일 역할과 구성

| 파일 | 담당 역할 |
| --- | --- |
| `tb_<module>.sv` | 클럭·리셋, DUT·tester 인스턴스와 신호 연결, 전체 timeout |
| `<module>_tester.sv` | 입력 공급, 출력 비교, 검사·오류 수 집계, 불일치 로그와 PASS/FAIL |
| `<module>_tb_data.vh` | 입력·기대 출력·비교 마스크 배열, 벡터 수와 실제 생성 설정 |
| `<module>_golden.py` | 입력 생성, 독립 기준 계산, 클럭별 상태 추적과 데이터 헤더 출력 |

모듈별 세 파일을 같은 TB 폴더에 둔다. 기존 `05_tb/unit`, `layer`, `system` 분류 안에 배치할 수 있으며, 아래는 단위 TB의 예시다. 전체 분류의 최종 배치와 Python 생성기의 저장 위치는 아직 정하지 않았다.

```text
project/05_tb/unit/tb_signed_adder32/
├── tb_signed_adder32.sv
├── signed_adder32_tester.sv
└── signed_adder32_tb_data.vh
```

데이터 헤더에는 자동 생성 파일임을 표시하며 Python을 통해 갱신한다. 수동으로 기대값을 고쳐 RTL에 맞추지 않는다. 생성기 파일명은 위 패턴을 기준으로 하고, 공통 출력 형식과 보조 함수는 재사용할 수 있다.

## 3. Python이 생성할 데이터

| 데이터 | 내용 |
| --- | --- |
| 입력 벡터 | 각 단계에서 tester가 DUT에 공급할 데이터·설정·제어 값 |
| 기대 출력 | 명세와 동일한 정수 연산 및 상태 전이로 계산한 모든 출력 |
| 비교 시점 | 입력 공급 전 확인할 값과 입력 변경 후 안정화된 값을 구분 |
| 비교 마스크 | 명세상 값이 정의되지 않은 출력·비트에 한해 비교 제외 범위 명시 |
| 생성 정보 | 벡터 수, 폭·parameter, 소수 비트·shift, 사용한 seed 등 재현 정보 |

Signed 값은 폭에 맞는 2의 보수 비트 패턴으로 저장한다. 배열 포트의 lane 순서와 32비트 워드의 첫 바이트 [7:0] 배치를 명시한다.

입력은 기본 동작, 0·양수·음수·표현 범위 경계, 연속 처리와 제어 신호 공백을 포함하도록 모듈별로 구성한다. 임의 입력을 사용할 경우 seed를 기록한다. 사례 수와 구체적인 seed는 아직 확정하지 않았다.

`valid=0`이라는 이유만으로 데이터 출력을 모두 비교에서 제외하지 않는다. 명세상 값이 정해지는 출력은 계속 비교한다. 비교 마스크는 미구현 동작이나 불일치를 숨기는 용도로 사용하지 않는다.

## 4. 입력 공급과 비교 시점

클럭·리셋은 TB에서 발생시키며, Python 기준 모델도 같은 reset 조건과 초기 상태를 사용한다. 기본 실행의 reset은 명세대로 시작 시 수행하고, 펄스 길이와 해제 시점은 구현 전에 정한다.

순차 모듈은 참고 프로젝트의 다음 흐름을 따른다.

1. 상승 에지와 떨어진 시점에서 이전 입력으로 만들어진 출력을 기대값과 비교한다.
2. 현재 벡터의 입력을 공급한다.
3. 조합회로 안정화 후 다시 확인한다. 조합 출력은 새 입력에 대한 값, 레지스터 출력은 상승 에지 전 유지해야 할 값을 비교한다.
4. 다음 상승 에지에서 DUT가 입력을 처리한다.
5. 다음 벡터로 진행한다. 마지막 입력의 결과도 빠짐없이 비교하도록 필요한 마무리 단계를 포함한다.

조합 모듈은 입력 공급과 안정화 후 기대값을 비교한다. 지연량, 샘플링 지점과 필요한 마무리 단계는 각 모듈의 지연에 맞춰 정의한다. 구체적인 시간 간격은 아직 정하지 않았다.

연산 결과만 맞고 레지스터 출력이 상승 에지 전에 변하는 경우, 또는 조합 경로에 예상하지 않은 레지스터가 추가된 경우도 검출하도록 기대값을 준비한다.

## 5. 수치·메모리 기준

수치 규칙의 원본은 [명세 2절](architecture.md#2-수치-형식과-양자화)이다.

- 입력·weight·bias·레이어 출력은 signed 8비트다.
- 곱셈·adder tree·부분합·누산·결과 레지스터는 signed 32비트다.
- Bias는 부호 확장 후 shift로 정렬하고 누산기의 초깃값으로 사용한다.
- 출력 변환은 산술 우측 shift로 하위 비트를 버린 뒤 -128~127 포화다.
- FC1·FC2는 ReLU를 적용하고 FC3는 적용하지 않는다.
- 초기 F와 shift는 명세의 확정값을 사용한다. 오프라인 입력·weight·bias의 nearest-even 변환과 RTL 출력의 비트 버림을 구분한다.

기존 [generate_golden.py](../03_model/generate_golden.py)는 이미지 한 장의 BRAM 초기화 데이터, 레이어별 출력·부분합·누산 정답을 생성한다. 이 데이터는 연산 정답이며 클럭별 출력 벡터 자체는 아니다. 모듈별 생성기에서 재사용할 때 입력 공급 순서와 지연을 반영해 `.vh`로 변환한다.

메모리 검증에서는 초기화한 주소와 아직 쓰지 않은 주소를 구분한다. 초기화하지 않은 BRAM을 임의로 0이라고 가정하지 않는다. 읽기 지연, 쓰기 시점, TB/추론 접근 선택, A/B 역할 전환과 이전 데이터 유지도 검증한다.

FC3 더미 2개는 0으로 저장하며, ARGMAX는 실제 출력 10개만 signed 비교한다. 동점에서는 작은 인덱스를 유지한다.

## 6. 모듈별 검증 항목과 진행 순서

아래는 의존 관계에 따른 권장 순서다. 실제 구현 시작 모듈과 세부 사례는 해당 작업을 시작할 때 정한다.

| 단계 | 대상 | 주요 검증 항목 |
| --- | --- | --- |
| 1 | register_en, delay_line, signed_adder32 | reset·enable·유지·단계별 전달·signed 계산 |
| 2 | 곱셈, bias 정렬, ReLU, shift, 포화, 워드 분리·결합 | 음수·경계값·소수점 정렬·lane 순서 |
| 3 | dot_product4, MAC array | 균형 트리 계산, MAC 입력단을 포함한 세 레지스터 단계, 공통 valid와 공백 전달 |
| 4 | 누산기·후처리 | bias 초기화, 누산, 결과 저장, 다음 bias와 동시 처리, 조합 후처리 |
| 5 | RAM·Memory wrapper | 초기화·읽기·쓰기·주소·bank·핑퐁·TB 접근 선택 |
| 6 | LUT·카운터·주소·파이프라인 제어·ARGMAX | 레이어별 설정, N 공백, 주소 지연, signed 순차 비교와 동점 |
| 7 | Control unit과 레이어 경로 | FC1·FC2·FC3 공통 동작, 중첩 실행과 레이어 전환 |
| 8 | mlp_top | TB 포트 초기화, start/busy/done, 레이어별 저장값과 최종 prediction |

하위 모듈도 각자의 입력·출력을 직접 검증한다. 상위 검증에서는 같은 하위 모듈이 연결된 결과와 전체 시점 관계를 확인한다.

## 7. 판정과 기록

- 정의된 출력은 비트 단위로 비교한다. `!==` 비교로 예상하지 않은 X/Z도 불일치로 검출한다.
- 선언 폭·parameter와 생성 데이터의 설정이 다르면 검사를 진행하지 않고 오류로 처리한다.
- Timeout, 불일치, 벡터 누락 또는 실제 비교 없이 종료한 경우 PASS로 처리하지 않는다.
- 오류가 없고 예정된 검사를 모두 완료했을 때 PASS로 판정한다.
- 불일치 로그에는 모듈명, 벡터 번호·시점, 신호명, 실제값과 기대값을 남긴다. 배열 출력은 lane도 식별한다.
- 생성 설정과 데이터 출처, 실행 도구·결과를 재현할 수 있게 기록한다. 실제 파일 위치와 실행 명령은 구현 시 정한다.

컴파일·계층 전개 통과와 기능 검증 PASS를 구분한다. 현재 RTL은 구조와 배선 단계이며, 기존 Python 정확도나 golden 생성 성공을 RTL 기능 검증 결과로 간주하지 않는다.

## 8. 남은 구체화

- 전체 TB 분류와 모듈별 폴더 배치, Python 생성기 저장 위치 및 실행 명령.
- TB 클럭 주기, reset 펄스 길이·해제 시점, 안정화 후 샘플링 간격과 timeout.
- 모듈별 사례 수, seed, parameter 조합, 비교 시점과 마스크 정의.
- 명세에서 아직 정하지 않은 미사용·범위 밖 주소 및 동시 요청의 처리.
- 개별 연산기의 범위 밖 입력·오버플로 동작처럼 추가 정의가 필요한 경계 조건.
- Control FSM 인코딩과 각 하위 제어 모듈의 미확정 세부 동작에 대한 기대값.
- 최초 작성할 TB 세트와 실제 구현·시뮬레이션 일정.

미정 동작은 기대값을 임의로 확정해 생성하지 않는다. 해당 사항을 정한 뒤 생성기와 tester에 함께 반영한다.
