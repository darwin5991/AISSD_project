# Control unit 검증 명세서

> **2026-11-10 명세 개정:** MAC 입력·가중치 레지스터 1단을 추가해 데이터·valid 경로를 3단으로 변경했다. MAC·Control RTL과 검증환경 코드를 3단 명세에 맞게 수정했고 새 검증 데이터·헤더 5종을 생성했다. 생성기 내부 검사는 PASS했지만 새 RTL의 테스트·시뮬레이션·합성·배치배선은 아직 실행하지 않았다. [변경 범위와 일정](../mac_input_pipeline.md)을 따른다. 기존 실행 기록은 이전 구조의 이력으로 보존한다.

출처: [RTL 검증 계획](../verification.md). 공통 규칙과 해당 모듈의 검증 항목을 원문에서 옮겼다. 이후 사용자가 확정한 사항을 반영하며, 나머지 미정 사항은 확정하지 않는다.

## 1. 검증 방식

이 문서는 공통 검증 환경과 사용자가 확정한 Control 단독 검증 조건을 함께 기록한다. FSM은 사용자 확정에 따라 3비트 이진 인코딩으로 구현하며, 정상 추론 검사는 기존 외부 출력 기준을 유지한다.

- 모듈별로 TB, tester, 데이터 헤더를 한 세트로 구성한다.
- Python에서 테스트 입력과 기대 출력을 미리 계산하고 파일로 생성한다.
- Tester는 생성된 입력을 공급하고 기대값과 비교한다. RTL과 같은 연산을 다시 구현해 정답을 계산하지 않는다.
- 데이터 출력뿐 아니라 valid, 주소, enable, busy, done 등 해당 모듈의 모든 출력 포트를 검증 대상으로 둔다.
- 순차 출력과 조합 출력을 구분해 값과 변화 시점을 확인한다.
- 시점 판단은 명세를 따른다. 기준 모델은 명세에서 작성하고, DUT의 실제 출력을 기대값으로 사용하지 않는다.

참고한 deit_fpga의 단위 TB는 TB와 tester를 분리하고, tester에서 자동 생성된 `<module>_tb_data.vh`를 include한다. 참고 프로젝트의 Top TB는 tester 역할을 TB 내부에 포함하지만, AISSD에서는 Top도 TB와 tester를 분리하는 구성을 따른다.

사용자가 지정한 `deit_fpga/tb/`에서 다음 소스를 읽고 구조를 확인했다. 참고 프로젝트의 시뮬레이션은 실행하지 않았다.

- `tb_mac_array/tb_mac_array.v`, `mac_array_tester.v`, `mac_array_tb_data.vh`: TB의 클럭·reset·DUT/tester 연결·timeout, tester의 데이터 헤더 include·parameter 일치 검사·하강 에지 비교 후 입력 공급·오류 집계·PASS/FAIL 출력을 확인했다.
- `tb_sm_rowsum_acc/tb_sm_rowsum_acc.v`, `sm_rowsum_acc_tester.v`: TB와 tester 분리, valid와 데이터를 함께 비교하는 구성을 확인했다. 이 tester의 `#2` 중간 시점 추가 검사는 AISSD에 적용하지 않으며, 확정한 하강 에지 비교 방식을 따른다.
- `tb_vt_top/tb_vt_top.v`: Top TB 내부에 입력 공급·비교 역할이 함께 있는 구성을 확인했다. AISSD의 Top은 기존 확정대로 TB와 tester를 분리한다.

참고 소스의 reset 극성·유지 길이·데이터와 모듈 구조는 그대로 옮기지 않는다. AISSD에서 확정한 reset·수치 형식·실제 MNIST 데이터·모듈 구성을 따른다.

## 2. 파일 역할과 구성

| 파일 | 담당 역할 |
| --- | --- |
| `tb_<module>.sv` | 클럭·리셋, DUT·tester 인스턴스와 신호 연결, 전체 timeout |
| `<module>_tester.sv` | 입력 공급, 출력 비교, 검사·오류 수 집계, 불일치 로그와 PASS/FAIL |
| `<module>_tb_data.vh` | 입력·기대 출력·비교 마스크 배열, 벡터 수와 실제 생성 설정 |
| `<module>_golden.py` | 입력 생성, 독립 기준 계산, 클럭별 상태 추적과 데이터 헤더 출력 |

모듈별 TB·tester·데이터 헤더 세 파일을 같은 TB 폴더에 둔다.

**사용자 확정: `05_tb/`의 분류는 `04_rtl/`의 구성을 따른다.** `common/`, `mac_array/`, `accumulator_postprocess/`, `memory/`, `controller/`로 구분한다. Top과 Control unit은 해당 RTL과 같이 `controller/`에 둔다.

**사용자 확정: Python golden 생성기는 `03_model/golden/`에 모아 두고, 실제 사용하는 `.vh` 파일은 해당 TB·tester와 함께 둔다.**

```text
project/05_tb/controller/
├── tb_control_unit.sv
├── control_unit_tester.sv
└── control_unit_tb_data.vh

project/03_model/golden/control_unit_golden.py
```

데이터 헤더에는 자동 생성 파일임을 표시하며 Python을 통해 갱신한다. 수동으로 기대값을 고쳐 RTL에 맞추지 않는다. 생성기 파일명은 위 패턴을 기준으로 하고, 공통 출력 형식과 보조 함수는 재사용할 수 있다.

## 3. Python이 생성할 데이터

| 데이터 | 내용 |
| --- | --- |
| 입력 벡터 | 각 단계에서 tester가 DUT에 공급할 데이터·설정·제어 값 |
| 기대 출력 | 명세와 동일한 정수 연산 및 상태 전이로 계산한 모든 출력 |
| 비교 시점 | 각 하강 에지의 입력 변경 전 비교 시점과 출력별 클럭 지연을 명시 |
| 비교 마스크 | 명세상 값이 정의되지 않은 출력·비트에 한해 비교 제외 범위 명시 |
| 생성 정보 | 벡터 수, 폭·parameter, 소수 비트·shift, 사용한 seed 등 재현 정보 |

Signed 값은 폭에 맞는 2의 보수 비트 패턴으로 저장한다. 배열 포트의 lane 순서와 32비트 워드의 첫 바이트 [7:0] 배치를 명시한다.

**사용자 확정: 최초 Top 검증은 MNIST test 이미지 0번(sample ID = 0) 한 장으로 수행하며, 대부분의 시뮬레이션 시나리오는 해당 이미지의 실제 추론 데이터를 사용한다.** 중간 모듈 검증도 같은 추론 과정에서 발생하는 실제 연산 입력과 중간 결과를 사용하며, 무작위 데이터를 기본 검증 입력으로 사용하지 않는다.

**사용자 확정: 최초 시나리오는 정상 추론 1회로 한다.** 초기화 → start → FC1 → FC2 → FC3 → ARGMAX → done을 검증한다. 실행 중 추가 start와 재실행 등 예외 시나리오는 최초 검증에 포함하지 않는다.

실제 데이터는 Python 기준 모델에서 생성한다. RTL의 출력을 기대값으로 사용하지 않는다. 동일 이미지의 입력·weight·bias·부분합·누산값·레이어별 출력을 모듈별 검증에 활용하고, 제어 신호의 기대값은 명세의 실행 일정에 따라 독립적으로 계산한다.

**사용자 확정: 무작위 데이터가 필요한 경우 seed는 42를 사용하고 기록한다.** 무작위 검증은 필요한 경우에만 보조적으로 사용한다. 기본 검증의 벡터 수는 이미지 0번의 실제 연산 과정에 따라 정하며, 모듈별 데이터 범위·추가 사례는 아직 확정하지 않았다.

같은 이미지 한 장의 추론을 기준으로 레이어 설정, 메모리 주소·enable, 파이프라인 제어, 레이어 전환과 ARGMAX의 기대값을 명세에서 계산한다. ARGMAX 데이터에는 실제 FC3 출력을 사용한다.

`valid=0`이라는 이유만으로 데이터 출력을 모두 비교에서 제외하지 않는다. 명세상 값이 정해지는 출력은 계속 비교한다. 비교 마스크는 미구현 동작이나 불일치를 숨기는 용도로 사용하지 않는다.

## 4. 입력 공급과 비교 시점

**사용자 확정: TB 클럭 주기는 10 ns(100 MHz)로 한다.**

**사용자 확정: 시뮬레이션 시간 단위는 1 ns, 시간 정밀도는 1 ps로 한다.**

클럭·리셋은 TB에서 발생시키며, Python 기준 모델도 같은 reset 조건과 초기 상태를 사용한다.

**사용자 확정: Reset은 비동기 active-low이며, 시뮬레이션 시작 시 3주기(30 ns) 동안 유지한 뒤 클럭 하강 에지에서 해제한다.**

**사용자 확정: 레지스터 출력과 조합 출력을 포함한 모든 출력은 클럭 하강 에지에서 기대값과 비교한다.** 출력 비교를 위해 별도 1 ns 지연을 두지 않는다.

입력 공급과 비교는 다음 순서로 진행한다.

1. 클럭 하강 에지에서 현재까지 유지한 입력과 내부 상태에 대한 모든 출력을 기대값과 비교한다.
2. 비교를 마친 뒤 다음 벡터의 입력·설정·제어 값을 공급한다. 해당 값은 다음 하강 에지의 비교를 마칠 때까지 유지한다.
3. 다음 상승 에지에서 DUT가 입력을 처리한다.
4. 다음 하강 에지에서 출력별로 명세에 정해진 클럭 지연을 반영한 기대값과 비교하고, 같은 순서로 반복한다.
5. 마지막 입력 뒤에도 필요한 파이프라인 지연만큼 검사를 이어가 마지막 결과까지 비교한다.

같은 하강 에지에서 새 입력 공급과 출력 비교를 수행할 때는 반드시 비교를 먼저 한다. 새 입력에 대한 조합 출력을 입력 변경과 동시에 비교하지 않는다. 별도의 클럭이 없는 조합 하위 모듈도 TB 클럭의 하강 에지를 비교 기준으로 사용한다.

**사용자 설계 방향: 큰 모듈은 내부 중간 레지스터가 있는 순차 경로를 사용한다.** 중간 레지스터 뒤의 조합 후처리는 허용하며, 출력단이 조합회로라는 이유만으로 추가 출력 레지스터를 요구하지 않는다.

출력별 순차·조합 여부와 클럭 지연은 각 모듈 명세를 따른다. Python 기준 모델도 같은 하강 에지에서 비교할 값을 생성한다.

## 5. Control unit 상세 검증 항목

이 절은 기존 [Control unit 설계 명세](../modules/control_unit.md), [architecture.md](../architecture.md), [Control unit RTL 포트](../../04_rtl/controller/control_unit.sv)를 근거로 검증 항목을 구체화한다. 새 설계값이나 미정 동작을 임의로 확정하지 않는다.

### 5.1. 검증 대상과 입출력

검증 대상은 `control_unit`과 그 내부에 연결된 제어 하위 모듈이다. 기존 포트는 입력 4개(`clk`, `rst_n`, `start`, `argmax_data`), 출력 18개다.

| 신호 | 방향 | 형식 | 역할 |
| --- | --- | --- | --- |
| clk | 입력 | 1비트 | 클럭 |
| rst_n | 입력 | 1비트 | 비동기 active-low reset |
| start | 입력 | 1비트 | 추론 시작 |
| argmax_data | 입력 | 32비트 | Memory wrapper의 in_data. ARGMAX에서 사용 |
| busy | 출력 | 1비트 | 전체 동작 진행 중 |
| done | 출력 | 1비트 | ARGMAX까지 완료한 1클럭 펄스 |
| prediction | 출력 | 4비트 | 최종 예측 인덱스 |
| buf_sel | 출력 | 1비트 | A/B 역할 선택 |
| in_addr | 출력 | 8비트 | 입력·ARGMAX 읽기 워드 주소 |
| in_en | 출력 | 1비트 | 입력·ARGMAX 읽기 |
| out_addr | 출력 | 7비트 | 출력 쓰기 워드 주소 |
| out_we | 출력 | 1비트 | 출력 쓰기 |
| weight_addr | 출력 | 15비트 | 가중치 읽기 주소 |
| weight_en | 출력 | 1비트 | 가중치 읽기 |
| bias_addr | 출력 | 8비트 | Bias 읽기 주소 |
| bias_en | 출력 | 1비트 | Bias 읽기 |
| mac_input_valid | 출력 | 1비트 | MAC array의 input_valid에 연결 |
| bias_load | 출력 | 1비트 | 누산기를 bias로 초기화 |
| bias_shift | 출력 | signed 6비트 | Bias 정렬 |
| result_load | 출력 | 1비트 | 완료된 누산값 보관 |
| relu_en | 출력 | 1비트 | ReLU 적용 여부 |
| output_shift | 출력 | unsigned 5비트 | 출력 정렬 |

**사용자 확정: 초기 Control tester는 외부 출력 18개를 검증 대상으로 하며, 내부 FSM·카운터를 직접 관측해서 비교하지 않는다.** 각 외부 출력의 비교 유효 조건은 기존 명세를 따른다. FSM 인코딩을 기대값으로 임의 고정하지 않는다.

**사용자 확정: `argmax_data`는 tester가 미리 생성한 이미지 0번의 실제 FC3 출력 데이터를 공급한다.** Memory wrapper의 읽기 지연 1클럭과 읽은 워드 유지 조건을 입력 벡터 일정에 반영한다. Control 단독 검증을 위한 별도 메모리 응답 모델은 사용하지 않는다.

### 5.2. 출력별 비교 기준

| 출력 | 기존 설계 명세에 따른 확인 항목 |
| --- | --- |
| `busy` | Reset 후 0, start 수락 후 1, FC3 저장 이후 ARGMAX까지 1 유지, 최종 비교 완료 시 0 |
| `done` | Reset 후 0, 최종 비교 완료 시 1클럭 동안 1, 다음 클럭에 0 복귀 |
| `prediction` | Reset 후 0, `done=1`에서 Python 기준 모델의 최종 예측 인덱스와 일치 |
| `buf_sel` | FC1=0, FC2=1, FC3=0, ARGMAX=1 |
| `in_en`, `weight_en` | MLP의 입력·가중치 읽기 일정과 일치. 묶음 사이 N 공백에서는 새 읽기 중단 |
| `in_en` | ARGMAX에서는 버퍼 B의 워드 0·1·2를 정해진 일정에 따라 읽음 |
| `in_addr`, `weight_addr`, `bias_addr`, `out_addr` | 각 주소의 유효 조건에서 주소 계산식·묶음·레이어 시작 주소·쓰기 지연과 일치 |
| `bias_en` | 각 출력 묶음의 첫 입력·가중치 읽기와 함께 해당 bias 워드 읽기 |
| `mac_input_valid` | MLP 읽기 수행 여부를 1클럭 지연한 값과 일치 |
| `bias_load` | 레이어 첫 bias 읽기 다음 에지, 이후에는 이전 묶음의 `result_load`와 같은 에지에 발생. 마지막 묶음 결과에서는 다음 bias 초기화 없음 |
| `result_load` | 각 묶음의 마지막 읽기 R에서 5클럭 뒤 결과 보관 |
| `out_we` | 각 묶음의 마지막 읽기 R에서 6클럭 뒤 출력 저장 |
| `bias_shift`, `output_shift`, `relu_en` | FC1~FC3의 레이어별 초기 LUT 값과 후처리 설정 유지 조건 확인. ARGMAX 구간에서는 비교 제외 |

주소 출력의 비교 유효 조건은 기존 설계에서 다음과 같이 확정돼 있다.

| 주소 출력 | 주소가 유효한 조건 |
| --- | --- |
| `in_addr` | `in_en = 1` |
| `weight_addr` | `weight_en = 1` |
| `bias_addr` | `bias_en = 1` |
| `out_addr` | `out_we = 1` |

대응 enable이 0일 때 주소값은 제한하지 않으므로 해당 주소만 비교에서 제외한다. enable 자체와 같은 시점의 다른 정의된 출력은 계속 비교한다.

`prediction`은 reset과 `done=1` 시점에 비교한다. `done=0`이면 현재 최댓값 인덱스가 출력돼도 되고 이전 최종값 유지도 보장되지 않으므로, 해당 구간의 prediction에 임의 기대값을 부여하지 않는다.

**사용자 확정: ARGMAX 구간에서는 사용하지 않는 `bias_shift`, `output_shift`, `relu_en`을 비교에서 제외한다.** 이 구간의 `buf_sel=1`, 입력 읽기 주소·enable, `busy`, `done`과 유효한 `prediction` 등 다른 정의된 출력은 계속 검사한다. ARGMAX 외 구간의 비교는 기존 명세의 유효 조건을 따르며, 값이 정해지지 않은 미사용 구간은 별도로 정한다.

### 5.3. 레이어 설정·주소·버퍼 역할

| 레이어 | 입력 워드 수 N | 출력 묶음 수 | ReLU | 초기 bias_shift | 초기 output_shift |
| --- | ---: | ---: | ---: | ---: | ---: |
| FC1 | 196 | 128 | 1 | +3 | 10 |
| FC2 | 128 | 32 | 1 | +1 | 7 |
| FC3 | 32 | 3 | 0 | +2 | 7 |

| 레이어 | 각 가중치 bank의 시작 워드 주소 | Bias 시작 워드 주소 |
| --- | ---: | ---: |
| FC1 | 0 | 0 |
| FC2 | 25,088 | 128 |
| FC3 | 29,184 | 160 |

- FC1 입력은 A, 출력은 B이며 `buf_sel=0`이다.
- FC2 입력은 B, 출력은 A이며 `buf_sel=1`이다.
- FC3 입력은 A, 출력은 B이며 `buf_sel=0`이다.
- ARGMAX는 B를 입력 읽기 경로에 연결하므로 `buf_sel=1`이다.
- 내부 주소 단위는 32비트 한 워드다.
- 가중치 주소는 `레이어 weight 시작 주소 + 출력 묶음 번호 × 입력 워드 수 + 입력 워드 번호`다.
- Bias 주소는 `레이어 bias 시작 주소 + 출력 묶음 번호`다.
- `out_addr`는 마지막 읽기 시점의 출력 묶음 번호를 `out_we`와 정렬한 값이다. 현재 읽기 묶음 번호를 그대로 사용하지 않는다.
- 입력 워드 번호 0~N-1에서 읽고, 후속 묶음이 있으면 N에서 한 클럭 읽기를 쉰 뒤 다음 묶음으로 진행한다. 공백 중에도 이미 진행 중인 MAC·누산·저장 제어는 계속된다.
- 각 레이어의 마지막 묶음의 마지막 읽기 후에는 바로 DRAIN으로 전환한다.

### 5.4. 제어 이벤트와 파이프라인 지연

| 제어 이벤트 | 발생 조건과 시점 |
| --- | --- |
| 입력·가중치 읽기 | RUN에서 입력 워드 카운터가 `0~N-1`일 때 수행 |
| 묶음 사이 공백 | 다음 묶음이 있으면 입력 워드 카운터 N에서 한 클럭 동안 새 입력·가중치 읽기를 중단 |
| Bias 읽기 | 각 출력 묶음의 첫 입력·가중치 읽기와 함께 해당 bias 워드를 읽음 |
| `mac_input_valid` | MLP 입력·가중치 읽기 수행 여부를 1클럭 지연 |
| 레이어 첫 `bias_load` | 해당 레이어의 첫 bias 읽기 다음 상승 에지 |
| 후속 묶음 `bias_load` | 이전 묶음의 `result_load`와 같은 에지 |
| `result_load` | 해당 묶음의 마지막 입력 읽기 에지 R에서 5클럭 뒤 |
| `out_we` | 해당 묶음의 마지막 입력 읽기 에지 R에서 6클럭 뒤 |
| `out_addr` | 해당 묶음의 마지막 읽기 시점 출력 묶음 번호를 `out_we`와 맞춰 지연 |
| DRAIN 진입 | 해당 레이어 마지막 출력 묶음의 마지막 입력 읽기 후 |
| 다음 PREP 준비 | 해당 레이어 마지막 출력 저장 후 |

| 읽기 수행 에지 기준 | 동작 |
| --- | --- |
| R | 입력·가중치 BRAM 읽기 |
| R+1 | input_valid = 1로 signed 8비트 입력·가중치와 유효 표시 1단 저장 |
| R+2 | 등록된 입력·가중치의 곱셈 결과와 유효 표시 2단 저장 |
| R+3 | Adder tree 부분합과 유효 표시 3단인 psum_valid 갱신 |
| R+4 | psum_valid를 샘플링해 해당 부분합 누산 |
| R+5 | 출력 묶음의 마지막 읽기였다면 완료된 누산값을 결과 레지스터에 저장 |
| R+6 | 출력 묶음의 마지막 읽기였다면 후처리한 출력 4개를 BRAM에 기록 |

위 표의 에지는 기존 설계에서 정의한 상승 에지다. Golden 생성기는 해당 실행 일정을 공통 규칙의 하강 에지 비교 시점에 맞게 변환해 기대값을 만든다. 제어 신호가 상승 에지에서 사용되는 시점과 레지스터가 갱신된 뒤의 값을 구분한다.

- `bias_load`와 `result_load`의 동시 발생은 허용한다.
- `bias_load`와 MAC의 `psum_valid`가 같은 상승 에지에서 소비되면 안 된다. Control 단독 검증에서 이 조건을 확인할 경우에는 실제 읽기 일정과 개정 MAC의 3단 valid 전달 규칙으로 관계를 계산한다.
- 후처리의 ReLU·shift 설정은 결과 레지스터 저장 뒤 출력 BRAM 쓰기까지 유지한다.
- 레이어 전환에서 전체 reset을 다시 주지 않는다.

### 5.5. 시작·레이어 전환·완료

- Reset 뒤 `busy=0`, `done=0`, `prediction=0`을 확인한다. LUT·조합 출력까지 모두 reset 값 0으로 가정하지 않는다.
- **사용자 확정: Reset 해제 후 1클럭 대기하고, 다음 하강 에지의 출력 비교를 마친 뒤 `start`를 1클럭 공급한다.** 대기 구간에서 reset 이후의 초기 상태를 확인한다.
- Start 수락 에지 S에서 `busy=1`, S+1에서 FC1 준비, S+2에서 첫 입력·가중치·bias 읽기를 시작하는 일정을 확인한다.
- 이전 레이어의 마지막 출력 저장 에지 L 이후, L+1에서 다음 레이어 준비·버퍼 역할 전환, L+2에서 다음 레이어 첫 읽기를 수행한다.
- 이전 레이어 마지막 출력의 저장이 끝나기 전에 다음 레이어의 후처리 설정으로 변경하지 않는다.
- FC3 마지막 저장 이후에도 `busy=1`을 유지하고 PREP를 거쳐 ARGMAX로 진행한다.
- 최종 ARGMAX 비교가 끝난 에지에서 `busy=0`, `done=1`과 최종 prediction을 확인한다. 다음 클럭의 하강 에지에서도 검사해 done이 0으로 복귀하는지 확인한다.
- 초기 검증에는 정상 추론 1회만 포함한다. Busy 중 추가 start 및 재실행 시나리오는 현재 범위에 넣지 않는다.

### 5.6. 실제 FC3 데이터에 대한 ARGMAX

기존 설계의 ARGMAX 입력은 FC3 후처리가 끝나 버퍼 B에 저장된 signed 8비트 출력이다. FC3에서는 출력 shift·포화를 적용하고 ReLU는 적용하지 않는다. ARGMAX는 저장된 값의 크기를 비교하므로 `bias_shift`, `output_shift`, `relu_en`을 다시 적용하지 않는다. 이 구간의 세 설정 포트는 사용자 확정대로 비교에서 제외한다.

| 상승 에지 | 동작 |
| --- | --- |
| 0 | B의 워드 0 읽기 |
| 1 | 출력 0으로 최댓값·선택 인덱스 초기화 |
| 2~4 | 출력 1~3을 한 클럭에 하나씩 비교 |
| 5 | B의 워드 1 읽기 |
| 6~9 | 출력 4~7을 한 클럭에 하나씩 비교 |
| 10 | B의 워드 2 읽기 |
| 11 | 출력 8 비교 |
| 12 | 출력 9 비교 완료, busy = 0, done = 1 |

- FC3 저장 이후 B의 워드 0~2에 들어 있는 실제 출력 10개를 signed 8비트로 해석한다.
- 워드의 첫 바이트는 [7:0]이다. 워드 2의 마지막 더미 2개는 비교하지 않는다.
- 출력 0으로 초기화하고 출력 1~9를 순서대로 비교한다. 더 큰 값에만 갱신하고 동점이면 작은 인덱스를 유지한다.
- 읽은 워드는 해당 워드의 값을 처리하는 동안 유지한다.
- ARGMAX 동안에는 MLP 입력·가중치 MAC 연산과 출력 저장을 수행하지 않는다.
- 이미지 0번의 실제 데이터에 대한 최종 예측을 Python 기준값과 비교한다. 그 데이터에 없는 동점·경계 사례를 검사했다고 간주하지 않는다. 추가 사례는 별도로 정한다.

### 5.7. 하강 에지 벡터와 상승 에지 일정의 대응

이 절의 벡터 인덱스는 기존에 확정한 비교 후 입력 공급 순서를 표현한다. 아직 파일로 생성한 시뮬레이션 데이터나 실제 RTL 검증 결과는 아니다.

- Reset을 해제한 하강 에지 뒤 1클럭을 기다린 다음 하강 에지를 벡터 0으로 둔다.
- 벡터 k에서는 현재 출력을 먼저 비교하고, 이후 그 벡터에 기록된 `start`, `argmax_data`를 공급한다.
- 벡터 k의 입력은 뒤따르는 상승 에지에서 처리된다. 벡터 k+1의 기대값에는 그 처리가 반영된다.
- 벡터 0에서 start를 공급하고, 뒤따르는 start 수락 상승 에지를 S로 둔다. 벡터 k의 비교 시점은 S+k 상승 에지 직전의 하강 에지다.
- 벡터 1에서 start를 0으로 내려 start를 정확히 1클럭 공급한다. 이후 이번 정상 추론에서 start를 다시 주지 않는다.
- 주소·enable·load 같은 제어 출력은 다음 상승 에지에서 사용될 값이고, busy·done·prediction 같은 레지스터 출력은 앞선 상승 에지까지 처리된 결과다. 같은 벡터에서도 이 의미를 구분해 기대값을 계산한다.

| 벡터 | 비교할 기존 명세의 상태·출력 | 비교 후 공급할 start | 뒤따르는 상승 에지 |
| ---: | --- | ---: | --- |
| 0 | Reset 해제 후 대기 상태. busy=0, done=0, prediction=0 확인 | 1 | S: start 수락 |
| 1 | S에서 반영된 busy=1, done=0. FC1 준비 구간 | 0 | S+1: FC1 준비 |
| 2 | S+2에서 첫 입력·weight·bias 읽기에 사용할 주소·enable | 0 | S+2: FC1 첫 읽기 |
| 이후 | 각 레이어의 읽기·공백·결과 보관·출력 쓰기 및 ARGMAX 일정 | 0 | 해당 벡터의 다음 상승 에지 |

상승 에지 R에서 소비되는 제어 이벤트는 R 직전 하강 에지 벡터에서 검사한다. 상승 에지 R에서 갱신된 상태·결과는 R 다음 하강 에지 벡터에서 검사한다. 동일한 숫자 R을 제어 이벤트와 처리 후 결과의 벡터 인덱스로 혼용하지 않는다.

### 5.8. 실제 모델 크기에서 계산한 MLP 일정

아래 수치는 기존 N·출력 묶음 수, 묶음 사이 한 클럭 공백, 마지막 읽기+6의 저장, 레이어 전환+2의 첫 읽기로 계산한 명세상 기대 일정이다. 실제 RTL을 실행한 결과가 아니다.

| 레이어 | N | 묶음 수 G | 입력·weight 읽기 수 | 묶음 사이 공백 수 | 첫 읽기 에지 | 마지막 읽기 에지 | 마지막 저장 에지 |
| --- | ---: | ---: | ---: | ---: | --- | --- | --- |
| FC1 | 196 | 128 | 25,088 | 127 | S+2 | S+25,216 | S+25,222 |
| FC2 | 128 | 32 | 4,096 | 31 | S+25,224 | S+29,350 | S+29,356 |
| FC3 | 32 | 3 | 96 | 2 | S+29,358 | S+29,455 | S+29,461 |

각 레이어의 첫 읽기를 F라 하면, 묶음 g(0~G-1)의 첫 읽기는 `F + g*(N+1)`, 마지막 읽기는 `F + g*(N+1) + N-1`이다. 마지막 묶음 뒤에는 새 읽기 공백을 추가하지 않고 DRAIN의 남은 이벤트를 처리한다.

정상 추론 1회에서 명세상 기대 이벤트 수는 다음과 같다.

| 이벤트 | 기대 횟수 |
| --- | ---: |
| MLP 입력·weight 읽기 | 29,280 |
| MLP mac_input_valid 활성 클럭 | 29,280 |
| 묶음 사이 새 입력·weight 읽기 공백 | 160 |
| Bias 읽기 | 163 |
| Bias 초기화 | 163 |
| 결과 레지스터 보관 | 163 |
| 출력 워드 쓰기 | 163 |
| ARGMAX 워드 읽기 | 3 |
| ARGMAX 초기화 | 1 |
| ARGMAX 후속 클래스 비교 | 9 |
| done 활성 클럭 | 1 |

Bias 초기화 163회에는 레이어 첫 초기화 3회와 후속 묶음 초기화 160회가 포함된다. Control 외부 in_en의 읽기는 MLP 29,280회와 ARGMAX 3회를 구분한다. 내부 ARGMAX 초기화·비교 횟수는 기대값을 계산하는 일정이며, 내부 포트를 직접 관측한다는 의미가 아니다.

### 5.9. ARGMAX 입력 공급과 종료 벡터

ARGMAX의 첫 워드 읽기 상승 에지를 A로 둔다. **사용자 확정: FC3 마지막 출력 저장 에지 L에서 2클럭 뒤인 L+2에 ARGMAX 첫 워드를 읽는다.** L+1은 ARGMAX 준비 PREP다. 5.8절의 계산에 따라 A는 S+29,463이다.

- A, A+5, A+10에서 각각 FC3 출력 워드 0, 1, 2를 읽는 일정을 사용한다.
- Tester는 A 다음 하강 에지의 비교를 마친 뒤 워드 0을 공급한다. 그러면 A+1에서 출력 0으로 초기화할 때 읽기 지연 1클럭에 대응하는 데이터가 입력돼 있다.
- 같은 방식으로 A+5 다음 하강 에지에서 워드 1을, A+10 다음 하강 에지에서 워드 2를 공급한다. 각 워드는 해당 워드의 값들을 처리하는 동안 유지한다.
- 이 공급 시점은 하강 에지 비교 후 입력 변경 규칙과 기존 ARGMAX 상승 에지 일정을 연결한 것이다. 기대값은 사전 생성하며, tester가 DUT 출력에 맞춰 기대값을 재계산하지 않는다.
- **사용자 확정: ARGMAX 이전에는 사용하지 않는 `argmax_data`를 0으로 공급한다.** ARGMAX 구간부터 사전 생성한 실제 FC3 출력 워드를 정해진 시점에 공급한다.
- 최종 비교 완료는 A+12 상승 에지다. A+12 다음 하강 에지에서 done=1, busy=0, 최종 prediction을 검사한다.
- 그 다음 하강 에지까지 한 클럭 더 검사해 done=0 복귀를 확인한 뒤 정상 실행을 마친다.
- **사용자 확정: ARGMAX 준비 PREP와 완료 후 IDLE에서는 미사용 `bias_shift`, `output_shift`, `relu_en`을 비교에서 제외한다.** 이 두 구간의 `buf_sel`은 입력 읽기 또는 출력 쓰기처럼 메모리 접근이 있을 때 비교한다. ARGMAX 진행 중 `buf_sel=1` 검사 규칙은 유지한다.

### 5.10. Control 데이터 헤더의 신호별 배열 형식

**사용자 확정: Control의 `.vh`는 신호별 배열 방식으로 구성한다.** 입력·기대 출력·비교 마스크를 신호 이름으로 구분하고, 각 배열의 인덱스는 같은 하강 에지 벡터 번호를 뜻한다. **사용자 확정: 비교 마스크는 신호당 벡터별 1비트로 두며, 1이면 해당 신호 전체를 비교하고 0이면 해당 신호를 비교에서 제외한다.**

| 데이터 | 내용 |
| --- | --- |
| 생성 정보 | sample ID 0, 체크포인트·입력 데이터 출처, 수치 설정, 헤더 형식 버전 |
| 길이·시간 설정 | 벡터 수, 10 ns 클럭, 1 ns / 1 ps, 예상 전체 실행 사이클, timeout=예상+100클럭 |
| 입력 배열 | 벡터별 start와 argmax_data. clk와 rst_n은 TB에서 생성 |
| 기대 출력 배열 | 출력 포트별 실제 폭·signed 여부에 맞춘 18개 기대값 배열 |
| 비교 마스크 | 출력 포트별 벡터당 1비트. 1=신호 전체 비교, 0=해당 신호 비교 제외 |

참고 TB처럼 신호별 배열을 두고 tester가 해당 포트의 배열을 직접 비교한다. 벡터 기대값은 현재 벡터의 입력을 새로 공급하기 전의 출력이며, 같은 인덱스의 새 입력에 대한 즉시 결과를 뜻하지 않는다.

아래는 두 벡터의 busy·done 기대값만 저장하는 신호별 배열 예시다. 실제 헤더의 벡터 수는 전체 일정에서 계산한다.

신호별 배열 예시:

```systemverilog
localparam integer NVEC = 2;
logic tb_exp_busy [0:NVEC-1];
logic tb_exp_done [0:NVEC-1];
initial begin
    tb_exp_busy[0] = 1'b0; tb_exp_done[0] = 1'b0;
    tb_exp_busy[1] = 1'b1; tb_exp_done[1] = 1'b0;
end
```

Tester는 `tb_exp_busy[i]`, `tb_exp_done[i]`처럼 신호 이름으로 기대값을 직접 참조한다.

A=S+29,463이므로 최종 ARGMAX 비교 완료는 S+29,475다. 벡터 29,476에서 done=1·busy=0·최종 prediction을 검사하고, 벡터 29,477에서 done=0 복귀를 확인한다. 따라서 개정 시나리오의 하강 에지 비교 벡터는 0~29,477, 총 29,478개다. Timeout의 예상 전체 실행 사이클은 초기 reset·대기와 이 마지막 검사까지 포함해 생성기가 계산한다.

### 5.11. 생성기의 입력과 결과 보존

- **사용자 확정: Control 생성기의 실제 FC3 데이터는 기존 `generate_golden.py`가 만든 `golden.npz`에서 가져온다.** Control 생성기에서 체크포인트를 다시 불러 추론하지 않는다.

- 원본 데이터가 없거나 설정이 다르면 준비 오류로 처리한다. 기존 확정대로 데이터 생성기를 자동 실행해 복구하지 않는다.
- **사용자 확정: Control 생성기를 실행하면 `05_tb/controller/control_unit_tb_data.vh`를 갱신한다.** 실제 TB는 이 고정 위치의 헤더를 사용한다.
- **사용자 확정: 생성 결과 원본은 `07_runs/`의 새 실행 폴더에 보존한다.** 생성한 헤더와 실제 생성 설정, 원본 데이터 출처를 함께 보존하며 이전 실행 결과는 덮어쓰지 않는다.
- TB 폴더의 사용 헤더가 어떤 생성 실행에서 왔는지 추적할 수 있도록 생성 정보에 실행 ID를 기록한다.


개정 3단 MAC에 맞춘 전체 Top 재현 시점은 T=265,018이다. 초기화·읽기 응답 규칙과 비교 범위·마스크 정책은 유지하며, 지연·단계 경계·예상 길이는 [개정 일정](../mac_input_pipeline.md)에 따른다. 생성기·tester·실행 타깃 코드와 실제 RTL은 개정했고 새 헤더를 생성했다. 생성 검사 외 테스트·RTL 시뮬레이션은 미실행이므로 기존 PASS를 새 명세의 검증 결과로 사용하지 않는다.

### 5.12. 구현된 생성기와 실행 방법

생성기는 [control_unit_golden.py](../../03_model/golden/control_unit_golden.py)다. NumPy가 설치된 Python 환경에서 저장소 루트를 기준으로 실행한다. 원본 실행 폴더에는 `manifest.json`과 그 manifest의 해시에 일치하는 `golden.npz`가 모두 있어야 한다.

```powershell
python project/03_model/golden/control_unit_golden.py --source-run project/07_runs/golden_sample_00000_20261106_063924_763427
```

위 원본 실행 경로는 실제 데이터를 보존한 폴더로 지정한다. 원본 데이터가 누락되면 생성기는 오류로 끝나며, 상위 데이터 생성이나 체크포인트 추론을 자동 실행하지 않는다. `--output-dir <새 경로>`로 결과 폴더를 지정할 수도 있으며, 기존 결과 폴더를 덮어쓰지 않는다.

생성 결과는 다음과 같다.

```text

├── vectors/
│   ├── control_unit_tb_data.vh
│   └── control_unit_vectors.npz
```

원본 데이터의 sample ID·수치 설정·레이어 설정·픽셀 해시·NPZ 해시와 signed ARGMAX 결과를 확인한 뒤 벡터를 생성한다. 생성 후 일정 불변 조건과 NPZ 재로딩을 확인하고, 보존한 헤더와 동일한 파일을 `05_tb/controller/control_unit_tb_data.vh`에 갱신한다. 입력 검증이 실패하면 기존 TB 헤더를 유지한다.

실행 ID·원본 실행 참조·원본 및 생성 파일 해시·소스 스냅샷·Git commit과 수정 여부·Python/NumPy 버전을 기록한다. 모든 배열은 신호별로 유지한다. 파일 크기를 줄이기 위해 헤더의 동일 값 연속 구간은 초기화 for 문으로 표현한다. 마스크가 0인 위치의 저장값은 비교 기준을 뜻하지 않는다.

생성기가 사용하는 TB 클럭 초기값은 0이다. Reset 해제는 세 번째 주기 끝의 하강 에지, 벡터 0은 한 주기 뒤인 네 번째 주기의 하강 에지다. 마지막 검사에서 종료하는 일정은 다음과 같다.

| 항목 | 명세상 값 |
| --- | ---: |
| 하강 에지 비교 벡터 수 | 29,475 |
| Reset·대기·마지막 검사까지의 예상 TB 사이클 | 29,478 |
| Timeout 사이클 | 29,578 |

```powershell
python -m unittest discover -s project/03_model/golden/tests -v
```

### 5.13. 구현된 TB와 tester

- [tb_control_unit.sv](../../05_tb/controller/tb_control_unit.sv): Control DUT와 tester를 연결하고, 10 ns 클럭·3주기 reset·전체 timeout을 담당한다. 내부 FSM이나 카운터를 직접 관측하지 않는다.
- [control_unit_tester.sv](../../05_tb/controller/control_unit_tester.sv): 같은 폴더의 `control_unit_tb_data.vh`를 include하고, 미리 생성한 입력·기대 출력·마스크만 사용한다. 메모리 응답이나 MLP 연산을 RTL에서 다시 계산하지 않는다.

Reset은 30 ns의 하강 에지에서 해제한다. Tester는 한 주기를 기다린 40 ns부터 벡터 0을 비교하고 입력 0을 공급한다. 마지막 벡터 29,474는 294,780 ns에 검사한다. TB의 timeout은 295,780 ns다. 비교를 위한 별도 시간 지연이나 파형 기록은 없다.

비교 전에 헤더 버전·sample ID·벡터 수·시간 설정·레이어 설정·포트 폭과 전체 입력/마스크/유효 기대값의 X/Z 여부를 검사한다. 각 하강 에지에서 출력 18개를 신호별 마스크에 따라 `!==`로 비교하고, 첫 불일치에서 신호·벡터·사이클·시간·실제/기대 HEX를 기록한 뒤 중단한다. 모든 비교가 끝난 경우에만 해당 벡터의 입력을 공급한다.

요약은 `[SUMMARY] module=control_unit result=PASS|FAIL vectors=완료/전체 checks=비교수 masked=제외수 errors=오류수` 형식이다. PASS는 마지막 done=0 벡터까지 완료하고, 비교 수가 0보다 크며, 모든 출력 신호를 한 번 이상 비교했을 때만 출력한다. Timeout·설정/데이터 오류·불일치는 FAIL 요약과 `$fatal`로 종료한다. 외부에서 조기 `$finish`가 발생한 경우에도 final 블록에서 미완료 FAIL을 남긴다.

현재 RTL에는 timescale 선언이 없으므로 xsim 계층 전개 시 `xelab -timescale 1ns/1ps`를 명시한다. 기본 실행은 `xsim <snapshot> -R -onerror quit -onfinish quit`를 사용하며 파형 로깅 명령은 넣지 않는다. 로컬 xsim 2025.1에서는 `$fatal` 발생 후에도 프로세스 종료 코드가 0이므로, 이후 Python 실행 스크립트는 종료 코드와 함께 최종 요약의 PASS/FAIL·검사 완료 여부를 판정해야 한다.

작성 시 xsim 2025.1로 다음을 확인했다.

- 초기 구조 단계에서 실제 Control RTL과 TB·tester의 컴파일 및 계층 전개 통과. 당시 실제 RTL 실행은 40 ns의 벡터 0에서 `busy=X`, 기대값 0으로 FAIL했다. 하위 RTL 내부 동작을 구현하기 전의 결과이며 현재 구현 검증 결과는 5.15절에 기록한다.
- Tester 자체 검사용 기대값 재생 모형으로 29,475개 벡터·442,015회 비교·88,535회 마스크 제외를 완료했다. 마스크로 제외한 출력은 X로 공급해도 PASS하며, 마지막 검사 시점은 294,780 ns다.
- 출력 18개 각각의 값 변경, 비교 대상 X, 마지막 done=0 불일치, 잘못된 마스크, 누락된 입력, timeout, 조기 종료의 총 24개 오류 검출 검사를 통과했다. 재생 모형은 실제 RTL 기준 모델로 사용하지 않는다.
- 로그는 `99_build/control_unit_tb_check/`, 재생 모형과 자체 검사 로그·요약은 `99_build/control_unit_checker_selftest/`에 둔다. WDB/VCD는 생성되지 않았다.

### 5.14. Python xsim 실행 스크립트

공통 실행 스크립트는 [run.py](../../90_scripts/run.py)다. 모듈별 소스·TB·헤더 설정은 [sim_targets.json](../../90_scripts/sim_targets.json)에 둔다. Python 표준 라이브러리만 사용하며, 저장소 루트에서 모듈 또는 TB 이름 하나를 선택한다.

```powershell
python project/90_scripts/run.py control_unit
python project/90_scripts/run.py tb_control_unit
```

Vivado 실행 파일이 PATH에 없으면 설치 위치를 지정한다.

```powershell
python project/90_scripts/run.py control_unit --vivado-bin C:/Xilinx/2025.1/Vivado/bin
```

- 한 번에 선택한 TB 하나만 실행한다. 이름을 생략하면 선택 방법을 알리고 종료하며, `--list`로 설정된 모듈/TB와 TB 작성 여부를 조회한다. 다른 모듈을 순회하거나 실패 후 자동 실행하지 않는다.
- 등록된 대상은 `control_unit`, `memory_wrapper`, `mac_array`, `accumulator_postprocess`, `mlp_top`이며 각각 `tb_<모듈명>`으로도 선택할 수 있다. 현재 TB·tester·데이터가 준비된 대상은 Control이다. 나머지는 파일 구성만 등록되어 있으며 미작성 파일이 있으면 준비 오류로 종료한다.
- 다른 TB를 추가할 때는 `sim_targets.json`에 `module`, `tb`, `header`, `data_kind`, `sources`를 등록한다. `sources`는 프로젝트 기준 상대 경로 또는 glob 패턴이며, 추가 대상마다 실행기를 복사하지 않는다. 형식 버전의 헤더 상수 이름은 `format_parameter`, 별도 고정 설정은 `expected_parameters`, 고정 출력 개수는 `output_count`로 선택 지정한다.
- 고정 TB 헤더의 `Run` 주석으로 생성 실행을 선택하고, 해당 manifest의 헤더 SHA-256·sample·시간 설정과 비교한다. 최신 실행을 자동 선택하지 않는다. 다른 위치에 보존한 생성 실행은 `--data-run <경로>`로 지정할 수 있지만 현재 TB 헤더와 일치해야 한다.
- 데이터 누락·설정 불일치는 준비 오류로 종료한다. Golden 생성기·체크포인트·NumPy를 호출하거나 헤더를 자동 갱신하지 않는다. 실행에는 TB 헤더와 생성 manifest가 필요하며 보존용 NPZ·헤더 복사본·소스 스냅샷은 다시 읽지 않는다.
- 실제 컴파일 소스와 헤더·실행기·대상 설정을 실행 폴더의 `source_snapshot/`에 복사하고 그 복사본을 사용한다. 선택한 대상에 등록된 소스만 컴파일한다. Control을 선택하면 Control 계층과 필요한 공통 모듈만, Top을 선택하면 전체 RTL 계층을 컴파일하고 선택한 TB만 계층 전개한다.
- `xvlog → xelab → xsim` 순서로 실행한다. 앞 단계가 실패하면 다음 단계를 시작하지 않는다. `xelab`에는 `-timescale 1ns/1ps -debug off`를 지정하며 파형은 기록하지 않는다.
- Tester 요약은 정확히 하나여야 하며, 선택한 모듈명·PASS·전체 벡터 완료·실제 비교 수 > 0·오류 수 0·비교/마스크 총수·최종 검사 시간을 확인한다. 요약 누락/중복, 다른 모듈의 요약, 불일치 또는 fatal 로그가 있으면 xsim 종료 코드가 0이어도 FAIL이다. 다른 TB도 5.13의 요약 형식을 사용하되 `module=`에는 해당 설정의 모듈명을 기록한다.
- 프로세스 종료 코드는 `0=PASS`, `1=RTL/tester FAIL`, `2=준비/도구 오류`, `130=사용자 중단`이다. TB의 29,578클럭 timeout과 별도로 도구 단계마다 기본 300초의 실제 시간 제한을 둔다. 필요한 경우 `--wall-timeout <초>`로 바꾸며, Windows에서 제한/중단이 발생하면 시작한 도구의 프로세스 트리를 종료한다.

실행마다 `07_runs/<선택한 대상>_xsim_<UTC 실행시각>/`을 새로 만든다. `logs/compile.log`, `logs/elaborate.log`, `logs/simulate.log`에 전체 텍스트 출력을 보존하고, 콘솔에는 단계와 tester의 상세 오류/최종 요약을 표시한다. `manifest.json`에는 선택한 모듈/TB·대상 설정·Git 상태·입력/소스 해시·도구 경로/버전·명령·단계별 종료 코드를, `metrics.json`에는 최종 결과·이유·검사 수를 기록한다. 시뮬레이터 빌드 파일은 같은 실행 ID의 `99_build/` 폴더에 둔다. 기존 결과는 덮어쓰지 않는다.

데이터 manifest의 `kind`는 대상 설정의 `data_kind`와 일치해야 한다. `timing`에는 `nvec`, `clock_period_ns`, `reset_cycles`, `expected_cycles`, `timeout_cycles`가, `outputs`에는 비교할 출력 신호 목록이 필요하다. 헤더에는 이에 대응하는 `NVEC`, `CLOCK_PERIOD_NS`, `RESET_CYCLES`, `EXPECTED_CYCLES`, `TIMEOUT_CYCLES`와 `SAMPLE_ID`, `TIME_UNIT_NS`, `TIME_PRECISION_PS` 상수를 둔다. 시작 대기·첫 벡터 시점·prediction은 manifest에 있는 경우만 공통 실행기에서 대조한다. 모듈별 FSM·연산 지연은 해당 생성기와 TB 명세에서 정한다.

생성 헤더는 SHA-256 검사를 사용하므로 `.gitattributes`에서 `05_tb/**/*.vh`와 `07_runs/**/*.vh`의 자동 줄바꿈 변환을 끈다.

## 7. 판정과 기록

### 공통 실행 환경

- **사용자 확정: 시뮬레이터는 xsim을 사용한다.**
- 기본 검증 결과는 tester의 자동 비교와 텍스트 로그로 확인한다.
- **사용자 확정: 파형 확인은 사용자가 별도로 요청한 경우에만 수행한다.** 파형 수동 확인을 기본 검증 절차나 PASS 판정의 필수 조건으로 두지 않는다.
- **사용자 확정: 기본 실행에서는 파형을 기록하지 않는다.** 파형 기록·확인은 사용자가 별도로 요청한 경우에만 설정한다.
- **사용자 확정: 데이터 생성기와 xsim은 분리해서 각각 수동 실행한다.** 생성기를 먼저 실행해 사용할 입력·기대값·데이터 헤더를 모두 준비하고, 이후 별도의 시뮬레이션 실행 스크립트를 실행한다.
- 시뮬레이션 실행 스크립트는 미리 생성한 데이터를 사용하며, 데이터 생성기를 자동 호출하거나 데이터를 자동 재생성하지 않는다.
- 생성 데이터의 설정 불일치는 기존 규칙대로 오류로 처리한다. 데이터가 누락된 경우에도 자동 생성하지 않고 준비 오류로 알린다.
- **사용자 확정: 시뮬레이션 실행 스크립트는 Python으로 작성하며, 한 번의 실행에서는 한 모듈만 검증한다.** 사용자가 검증할 모듈을 직접 골라 실행한다.
- 모듈별 Python 실행 스크립트를 따로 두거나, 공통 Python 실행 스크립트에서 한 모듈을 명시적으로 선택하는 구성을 사용할 수 있다. 구체적인 파일명·위치·명령은 구현 시 정한다.
- **사용자 확정: 전체 통합 검증은 Top 모듈의 TB·tester로 수행한다.** 모든 모듈 테스트를 한꺼번에 순회하는 실행 방식은 사용하지 않는다.

**사용자 확정: Timeout은 Python에서 계산한 예상 실행 사이클 수에 100클럭의 여유를 더한 값으로 한다.**

- 정의된 출력은 비트 단위로 비교한다. `!==` 비교로 예상하지 않은 X/Z도 불일치로 검출한다.
- 선언 폭·parameter와 생성 데이터의 설정이 다르면 검사를 진행하지 않고 오류로 처리한다.
- Timeout, 불일치, 벡터 누락 또는 실제 비교 없이 종료한 경우 PASS로 처리하지 않는다.
- 오류가 없고 예정된 검사를 모두 완료했을 때 PASS로 판정한다.
- 불일치 로그에는 모듈명, 벡터 번호·시점, 신호명, 실제값과 기대값을 남긴다. 배열 출력은 lane도 식별한다.
- **사용자 확정: 기본 로그는 불일치 상세와 최종 요약으로 한다.** 최종 요약에는 검사 수·오류 수와 PASS/FAIL을 남긴다. 정상 일치한 벡터의 값을 매번 출력하지 않는다.
- 생성 설정과 데이터 출처, 실행 도구·결과를 재현할 수 있게 기록한다. 실제 파일 위치와 실행 명령은 구현 시 정한다.

### 불일치 처리와 개별 모듈 실행

- **사용자 확정: 첫 불일치에서 해당 모듈의 실행을 중단한다.** 모듈명, 벡터 번호·시점, 신호명, 실제값·기대값을 기록하고 FAIL로 남긴다. 배열 출력은 lane도 식별한다.
- **사용자 확정: 실패 확인 후 어떤 모듈을 실행할지는 사용자가 직접 판단한다.** 실행 스크립트는 실패한 모듈에서 다른 모듈로 자동 이동하지 않는다.
- 검증하고 싶은 모듈만 직접 실행하고, 건너뛸 모듈은 실행하지 않는 방식으로 모듈 단위 선택·제외를 수행한다. 개별 테스트 케이스 선택·제외와 전체 모듈 일괄 실행은 현재 지원 범위에 포함하지 않는다.
- 다른 모듈을 실행하더라도 기존 실패 기록은 FAIL로 유지한다. 실행하지 않은 모듈을 검증 완료나 PASS로 처리하지 않는다.
- 기대값 변경이나 비교 마스크 확대로 불일치를 숨기지 않는다. 선택한 모듈에서는 정의된 출력을 계속 비교한다.

컴파일·계층 전개 통과와 기능 검증 PASS를 구분한다. Control 단독의 실제 검증 결과는 5.15절에 기록하며, 기존 Python 정확도나 golden 생성 성공을 RTL 기능 검증 결과로 간주하지 않는다.
