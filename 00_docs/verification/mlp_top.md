# Top 검증 명세서

출처: [RTL 검증 계획](../verification.md). 공통 규칙과 해당 모듈의 검증 항목을 원문에서 옮겼다. 이후 사용자가 확정한 사항을 반영하며, 나머지 미정 사항은 확정하지 않는다.

## 1. 검증 방식

**사용자 확정 범위: 현재 단계에서는 모듈에 공통으로 적용되는 검증 환경을 확정한다.** FSM 인코딩 등 개별 모듈의 구현에 종속된 사항은 해당 모듈을 구체화할 때 별도로 정한다.

- 모듈별로 TB, tester, 데이터 헤더를 한 세트로 구성한다.
- Python에서 테스트 입력과 기대 출력을 미리 계산하고 파일로 생성한다.
- Tester는 생성된 입력을 공급하고 기대값과 비교한다. RTL과 같은 연산을 다시 구현해 정답을 계산하지 않는다.
- 데이터 출력뿐 아니라 valid, 주소, enable, busy, done 등 해당 모듈의 모든 출력 포트를 검증 대상으로 둔다.
- 순차 출력과 조합 출력을 구분해 값과 변화 시점을 확인한다.
- 시점 판단은 명세를 따른다. 기준 모델은 명세에서 작성하고, DUT의 실제 출력을 기대값으로 사용하지 않는다.

참고한 deit_fpga의 단위 TB는 TB와 tester를 분리하고, tester에서 자동 생성된 `<module>_tb_data.vh`를 include한다. 참고 프로젝트의 Top TB는 tester 역할을 TB 내부에 포함하지만, AISSD에서는 Top도 TB와 tester를 분리하는 구성을 따른다.

사용자가 지정한 `deit_fpga/tb/`에서 다음 소스를 읽고 구조를 확인했다. 참고 프로젝트의 시뮬레이션은 실행하지 않았다.

- `tb_mac_array/tb_mac_array.v`, `mac_array_tester.v`, `mac_array_tb_data.vh`: TB의 클럭·reset·DUT/tester 연결·timeout, tester의 데이터 헤더 include·parameter 일치 검사·하강 에지 비교 후 입력 공급·오류 집계·PASS/FAIL 출력을 확인했다.
- `tb_sm_rowsum_acc/tb_sm_rowsum_acc.v`, `sm_rowsum_acc_tester.v`: TB와 tester 분리, valid와 데이터를 함께 비교하는 구성을 확인했다. 이 tester의 `#2` 중간 시점 추가 검사는 AISSD에 적용하지 않으며, 확정한 하강 에지 비교 방식을 따른다.
- `tb_vt_top/tb_vt_top.v`: Top TB 내부에 입력 공급·비교 역할이 함께 있는 구성을 확인했다. AISSD의 Top은 기존 확정대로 TB와 tester를 분리한다.

참고 소스의 reset 극성·유지 길이·데이터와 모듈 구조는 그대로 옮기지 않는다. AISSD에서 확정한 reset·수치 형식·실제 MNIST 데이터·모듈 구성을 따른다.

## 2. 파일 역할과 구성

| 파일 | 담당 역할 |
| --- | --- |
| `tb_<module>.sv` | 클럭·리셋, DUT·tester 인스턴스와 신호 연결, 전체 timeout |
| `<module>_tester.sv` | 입력 공급, 출력 비교, 검사·오류 수 집계, 불일치 로그와 PASS/FAIL |
| `<module>_tb_data.vh` | 입력·기대 출력·비교 마스크 배열, 벡터 수와 실제 생성 설정 |
| `<module>_golden.py` | 입력 생성, 독립 기준 계산, 클럭별 상태 추적과 데이터 헤더 출력 |

모듈별 TB·tester·데이터 헤더 세 파일을 같은 TB 폴더에 둔다.

**사용자 확정: `05_tb/`의 분류는 `04_rtl/`의 구성을 따른다.** `common/`, `mac_array/`, `accumulator_postprocess/`, `memory/`, `controller/`로 구분한다. Top과 Control unit은 해당 RTL과 같이 `controller/`에 둔다.

**사용자 확정: Python golden 생성기는 `03_model/golden/`에 모아 두고, 실제 사용하는 `.vh` 파일은 해당 TB·tester와 함께 둔다.**

```text
project/05_tb/controller/
├── tb_mlp_top.sv
├── mlp_top_tester.sv
└── mlp_top_tb_data.vh

project/03_model/golden/mlp_top_golden.py
```

데이터 헤더에는 자동 생성 파일임을 표시하며 Python을 통해 갱신한다. 수동으로 기대값을 고쳐 RTL에 맞추지 않는다. 생성기 파일명은 위 패턴을 기준으로 하고, 공통 출력 형식과 보조 함수는 재사용할 수 있다.

## 3. Python이 생성할 데이터

| 데이터 | 내용 |
| --- | --- |
| 입력 벡터 | 각 단계에서 tester가 DUT에 공급할 데이터·설정·제어 값 |
| 기대 출력 | 명세와 동일한 정수 연산 및 상태 전이로 계산한 모든 출력 |
| 비교 시점 | 각 하강 에지의 입력 변경 전 비교 시점과 출력별 클럭 지연을 명시 |
| 비교 마스크 | 명세상 값이 정의되지 않은 출력·비트에 한해 비교 제외 범위 명시 |
| 생성 정보 | 벡터 수, 폭·parameter, 소수 비트·shift, 사용한 seed 등 재현 정보 |

Signed 값은 폭에 맞는 2의 보수 비트 패턴으로 저장한다. 배열 포트의 lane 순서와 32비트 워드의 첫 바이트 [7:0] 배치를 명시한다.

**사용자 확정: 최초 Top 검증은 MNIST test 이미지 0번(sample ID = 0) 한 장으로 수행하며, 대부분의 시뮬레이션 시나리오는 해당 이미지의 실제 추론 데이터를 사용한다.** 중간 모듈 검증도 같은 추론 과정에서 발생하는 실제 연산 입력과 중간 결과를 사용하며, 무작위 데이터를 기본 검증 입력으로 사용하지 않는다.

**사용자 확정: 최초 시나리오는 정상 추론 1회로 한다.** 초기화 → start → FC1 → FC2 → FC3 → ARGMAX → done을 검증한다. 실행 중 추가 start와 재실행 등 예외 시나리오는 최초 검증에 포함하지 않는다.

실제 데이터는 Python 기준 모델에서 생성한다. RTL의 출력을 기대값으로 사용하지 않는다. 동일 이미지의 입력·weight·bias·부분합·누산값·레이어별 출력을 모듈별 검증에 활용하고, 제어 신호의 기대값은 명세의 실행 일정에 따라 독립적으로 계산한다.

**사용자 확정: 무작위 데이터가 필요한 경우 seed는 42를 사용하고 기록한다.** 무작위 검증은 필요한 경우에만 보조적으로 사용한다. 기본 검증의 벡터 수는 이미지 0번의 실제 연산 과정에 따라 정하며, 모듈별 데이터 범위·추가 사례는 아직 확정하지 않았다.

같은 이미지의 메모리 초기화 데이터와 FC1·FC2·FC3 기대 출력, 최종 prediction을 사용해 전체 추론을 검증한다.

`valid=0`이라는 이유만으로 데이터 출력을 모두 비교에서 제외하지 않는다. 명세상 값이 정해지는 출력은 계속 비교한다. 비교 마스크는 미구현 동작이나 불일치를 숨기는 용도로 사용하지 않는다.

## 4. 입력 공급과 비교 시점

**사용자 확정: TB 클럭 주기는 10 ns(100 MHz)로 한다.**

**사용자 확정: 시뮬레이션 시간 단위는 1 ns, 시간 정밀도는 1 ps로 한다.**

클럭·리셋은 TB에서 발생시키며, Python 기준 모델도 같은 reset 조건과 초기 상태를 사용한다.

**사용자 확정: Reset은 비동기 active-low이며, 시뮬레이션 시작 시 3주기(30 ns) 동안 유지한 뒤 클럭 하강 에지에서 해제한다.**

**사용자 확정: 레지스터 출력과 조합 출력을 포함한 모든 출력은 클럭 하강 에지에서 기대값과 비교한다.** 출력 비교를 위해 별도 1 ns 지연을 두지 않는다.

입력 공급과 비교는 다음 순서로 진행한다.

1. 클럭 하강 에지에서 현재까지 유지한 입력과 내부 상태에 대한 모든 출력을 기대값과 비교한다.
2. 비교를 마친 뒤 다음 벡터의 입력·설정·제어 값을 공급한다. 해당 값은 다음 하강 에지의 비교를 마칠 때까지 유지한다.
3. 다음 상승 에지에서 DUT가 입력을 처리한다.
4. 다음 하강 에지에서 출력별로 명세에 정해진 클럭 지연을 반영한 기대값과 비교하고, 같은 순서로 반복한다.
5. 마지막 입력 뒤에도 필요한 파이프라인 지연만큼 검사를 이어가 마지막 결과까지 비교한다.

같은 하강 에지에서 새 입력 공급과 출력 비교를 수행할 때는 반드시 비교를 먼저 한다. 새 입력에 대한 조합 출력을 입력 변경과 동시에 비교하지 않는다. 별도의 클럭이 없는 조합 하위 모듈도 TB 클럭의 하강 에지를 비교 기준으로 사용한다.

**사용자 설계 방향: 큰 모듈은 내부 중간 레지스터가 있는 순차 경로를 사용한다.** 중간 레지스터 뒤의 조합 후처리는 허용하며, 출력단이 조합회로라는 이유만으로 추가 출력 레지스터를 요구하지 않는다.

출력별 순차·조합 여부와 클럭 지연은 각 모듈 명세를 따른다. Python 기준 모델도 같은 하강 에지에서 비교할 값을 생성한다.

## 6. 수치·메모리 기준

수치 규칙의 원본은 [명세 2절](../architecture.md#2-수치-형식과-양자화)이다.

- 입력·weight·bias·레이어 출력은 signed 8비트다.
- 곱셈·adder tree·부분합·누산·결과 레지스터는 signed 32비트다.
- Bias는 부호 확장 후 shift로 정렬하고 누산기의 초깃값으로 사용한다.
- 출력 변환은 산술 우측 shift로 하위 비트를 버린 뒤 -128~127 포화다.
- FC1·FC2는 ReLU를 적용하고 FC3는 적용하지 않는다.
- 초기 F와 shift는 명세의 확정값을 사용한다. 오프라인 입력·weight·bias의 nearest-even 변환과 RTL 출력의 비트 버림을 구분한다.

기존 [generate_golden.py](../../03_model/generate_golden.py)는 이미지 한 장의 BRAM 초기화 데이터, 레이어별 출력·부분합·누산 정답을 생성한다. 이 데이터는 연산 정답이며 클럭별 출력 벡터 자체는 아니다. 모듈별 생성기에서 재사용할 때 입력 공급 순서와 지연을 반영해 `.vh`로 변환한다.

메모리 검증에서는 초기화한 주소와 아직 쓰지 않은 주소를 구분한다. 초기화하지 않은 BRAM을 임의로 0이라고 가정하지 않는다. 읽기 지연, 쓰기 시점, TB/추론 접근 선택, A/B 역할 전환과 이전 데이터 유지도 검증한다.

FC3 더미 2개는 0으로 저장하며, ARGMAX는 실제 출력 10개만 signed 비교한다. 동점에서는 작은 인덱스를 유지한다.

## 7. 판정과 기록

### 공통 실행 환경

- **사용자 확정: 시뮬레이터는 xsim을 사용한다.**
- 기본 검증 결과는 tester의 자동 비교와 텍스트 로그로 확인한다.
- **사용자 확정: 파형 확인은 사용자가 별도로 요청한 경우에만 수행한다.** 파형 수동 확인을 기본 검증 절차나 PASS 판정의 필수 조건으로 두지 않는다.
- **사용자 확정: 기본 실행에서는 파형을 기록하지 않는다.** 파형 기록·확인은 사용자가 별도로 요청한 경우에만 설정한다.
- **사용자 확정: 데이터 생성기와 xsim은 분리해서 각각 수동 실행한다.** 생성기를 먼저 실행해 사용할 입력·기대값·데이터 헤더를 모두 준비하고, 이후 별도의 시뮬레이션 실행 스크립트를 실행한다.
- 시뮬레이션 실행 스크립트는 미리 생성한 데이터를 사용하며, 데이터 생성기를 자동 호출하거나 데이터를 자동 재생성하지 않는다.
- 생성 데이터의 설정 불일치는 기존 규칙대로 오류로 처리한다. 데이터가 누락된 경우에도 자동 생성하지 않고 준비 오류로 알린다.
- **사용자 확정: 시뮬레이션 실행 스크립트는 Python으로 작성하며, 한 번의 실행에서는 한 모듈만 검증한다.** 사용자가 검증할 모듈을 직접 골라 실행한다.
- 모듈별 Python 실행 스크립트를 따로 두거나, 공통 Python 실행 스크립트에서 한 모듈을 명시적으로 선택하는 구성을 사용할 수 있다. 구체적인 파일명·위치·명령은 구현 시 정한다.
- **사용자 확정: 전체 통합 검증은 Top 모듈의 TB·tester로 수행한다.** 모든 모듈 테스트를 한꺼번에 순회하는 실행 방식은 사용하지 않는다.

**사용자 확정: Timeout은 Python에서 계산한 예상 실행 사이클 수에 100클럭의 여유를 더한 값으로 한다.**

- 정의된 출력은 비트 단위로 비교한다. `!==` 비교로 예상하지 않은 X/Z도 불일치로 검출한다.
- 선언 폭·parameter와 생성 데이터의 설정이 다르면 검사를 진행하지 않고 오류로 처리한다.
- Timeout, 불일치, 벡터 누락 또는 실제 비교 없이 종료한 경우 PASS로 처리하지 않는다.
- 오류가 없고 예정된 검사를 모두 완료했을 때 PASS로 판정한다.
- 불일치 로그에는 모듈명, 벡터 번호·시점, 신호명, 실제값과 기대값을 남긴다. 배열 출력은 lane도 식별한다.
- **사용자 확정: 기본 로그는 불일치 상세와 최종 요약으로 한다.** 최종 요약에는 검사 수·오류 수와 PASS/FAIL을 남긴다. 정상 일치한 벡터의 값을 매번 출력하지 않는다.
- 생성 설정과 데이터 출처, 실행 도구·결과를 재현할 수 있게 기록한다. 실제 파일 위치와 실행 명령은 구현 시 정한다.

### 불일치 처리와 개별 모듈 실행

- **사용자 확정: 첫 불일치에서 해당 모듈의 실행을 중단한다.** 모듈명, 벡터 번호·시점, 신호명, 실제값·기대값을 기록하고 FAIL로 남긴다. 배열 출력은 lane도 식별한다.
- **사용자 확정: 실패 확인 후 어떤 모듈을 실행할지는 사용자가 직접 판단한다.** 실행 스크립트는 실패한 모듈에서 다른 모듈로 자동 이동하지 않는다.
- 검증하고 싶은 모듈만 직접 실행하고, 건너뛸 모듈은 실행하지 않는 방식으로 모듈 단위 선택·제외를 수행한다. 개별 테스트 케이스 선택·제외와 전체 모듈 일괄 실행은 현재 지원 범위에 포함하지 않는다.
- 다른 모듈을 실행하더라도 기존 실패 기록은 FAIL로 유지한다. 실행하지 않은 모듈을 검증 완료나 PASS로 처리하지 않는다.
- 기대값 변경이나 비교 마스크 확대로 불일치를 숨기지 않는다. 선택한 모듈에서는 정의된 출력을 계속 비교한다.

컴파일·계층 전개 통과와 기능 검증 PASS를 구분한다. Control·Memory·MAC RTL은 각각 단독 검증을 통과했다. 최초 Top PASS는 실제 Top·Control과 임시 모델 3개를 연결한 결과다. 이후 실제 Memory로 교체한 Top 검증과 실제 MAC까지 연결한 Top 검증도 각각 PASS했다. 누산기·후처리는 임시 모델이므로 전체 실제 RTL 검증 완료를 뜻하지 않는다. Python 정확도나 golden 생성 성공도 RTL 기능 검증 결과로 간주하지 않는다.

## 8. Top 선행 검증의 확정 범위

**사용자 확정:** 실제 Top·Control RTL에 입력으로 읽기·연산을 수행하는 시뮬레이션 전용 모델을 연결한다. Golden 결과를 순서대로 내보내는 재생 모델을 사용하지 않는다.

- `05_tb/memory/models/memory_wrapper_model.sv`: 포트 기반 저장·1클럭 읽기·A/B 접근 전환. Reset은 저장 내용을 지우지 않는다.
- `05_tb/mac_array/models/mac_array_model.sv`: signed 곱셈·부분합의 2단 지연과 valid.
- `05_tb/accumulator_postprocess/models/accumulator_postprocess_model.sv`: bias 정렬·누산·결과 레지스터·ReLU·shift·포화.

모델은 실제 모듈과 이름·포트가 같다. `90_scripts/sim_targets.json`의 `mlp_top.sources`에서 컴파일할 파일을 선택한다. Top RTL에 모델 선택 분기를 추가하지 않는다. 실제 RTL로 교체할 때는 해당 모델 소스를 제외하고 실제 모듈과 필요한 하위 소스를 등록한다. `modeled_modules`와 `verification_scope`도 실제 구성에 맞게 갱신한다.

**사용자 확정:** 초기화한 모든 워드를 추론 전에 외부 TB 포트로 읽어 비교한다. 추론 중 레이어별 쓰기 enable·주소·버퍼 선택·데이터는 TB에서 읽기 전용으로 관측한다. 기대 일정이나 정답을 DUT 내부 상태에서 가져오지 않으며, 메모리 내용을 계층 경로로 읽거나 쓰지 않는다.

| 단계 | 검증 범위 |
| --- | --- |
| 초기화 | A 196 + B 128 + weight 4×29,280 + bias 163 = 117,607워드 외부 쓰기 |
| 초기 읽기 | 기록한 117,607워드 전체를 외부 읽기, 1클럭 응답과 비교 |
| 추론 | Start 1회, busy/done 일정, FC1 128·FC2 32·FC3 3워드 저장 관측 |
| 완료 | done 시 prediction, 다음 클럭 done=0 |
| 최종 읽기 | A 196·B 128워드 전체 비교. 덮어쓰지 않은 영역의 유지 포함 |

외부 출력 4개와 읽기 전용 관측 4개를 신호별 배열·마스크로 비교한다. Busy·done·쓰기 enable은 전 벡터에서 검사한다. Prediction은 reset 후 첫 벡터와 done에서, tb_rdata는 읽기 응답에서만 검사한다. 쓰기 주소·버퍼·데이터는 쓰기 enable일 때 검사한다. FC3 더미 2개도 저장값에 포함하며 ARGMAX에서는 제외한다.

전체 265,015벡터, 첫 비교 40 ns, 종료 2,650,180 ns, timeout 265,118주기다. 기대 비교는 913,467개이며 최초 불일치에서 중단한다. 미정 주소·동시 요청·오버플로 경계 사례를 임의로 추가하지 않는다.

## 9. 생성과 실행

저장된 연산 golden을 사용해 데이터를 먼저 생성한다. 생성기는 HEX hash·NPZ 배치·레이어 연결·최종 버퍼 유지·일정·벡터 NPZ 재읽기를 검사한 후 `.vh`를 게시한다.

```powershell
python project/03_model/golden/mlp_top_golden.py --source-run project/07_runs/golden_sample_00000_20261109_012337_273666
python project/90_scripts/run.py mlp_top
```

두 명령은 각각 수동 실행한다. Runner가 생성기를 자동 실행하지 않는다. `tb_mlp_top` 이름으로도 같은 타깃을 선택할 수 있다.

실행 기록은 `07_runs/mlp_top_xsim_<UTC>/`에 남기며 `verification_scope=top_with_behavioral_models`, `modeled_modules`를 기록한다. PASS는 `simulation_passed`와 `top_with_models_verified`로 표시하고 `rtl_verified=false`를 유지한다. 파형은 기록하지 않는다. 실제 MAC의 단독 검증과 Top 연결 검증은 통과했으며, 누산기 RTL의 구현과 단독 검증·전체 RTL 통합 검증·합성·타이밍 확인은 후속 작업이다.

## 11. 실제 Memory로 교체한 후속 검증 구성

사용자 요청에 따라 `mlp_top` 실행 타깃의 Memory 모델을 실제 RTL로 교체했다.

- 실제 RTL: Top·Control 및 `04_rtl/memory/`의 Memory wrapper와 하위 모듈 5개.
- 임시 모델: MAC array·누산기/후처리. `modeled_modules`에는 이 두 모듈만 기록한다.
- `memory_wrapper_model.sv`는 Top 컴파일 소스에서 제외한다. 모델 파일과 최초 선행 검증 기록은 보존한다.
- 기존 이미지 0번 Top golden·헤더·tester·비교 마스크와 265,015벡터의 실행 일정은 유지한다. Top 내부 배선은 변경하지 않는다.
- 초기화·전체 읽기·FC1~FC3 쓰기 관측·prediction·최종 버퍼 확인을 통해 실제 Control의 주소·enable·버퍼 전환과 실제 Memory의 연결을 검증했다.

MAC·누산기가 모델이므로 `verification_scope=top_with_behavioral_models`와 `rtl_verified=false` 원칙은 유지한다. 실행 명령은 기존 `python project/90_scripts/run.py mlp_top`과 같다.

컴파일 소스·메타데이터와 관련 문서·기존 실행기 테스트의 구성 기대값을 수정한 뒤, 사용자 요청에 따라 변경한 Top 타깃의 컴파일·계층 전개·xsim을 실행했다. 기존 생성 데이터와 비교 마스크는 변경하거나 재생성하지 않았다. 별도 실행기 테스트 스위트는 실행하지 않았다.

## 12. 실제 MAC으로 교체한 후속 검증 구성

MAC 단독 xsim PASS 후 `mlp_top` 실행 타깃의 MAC 모델을 실제 RTL로 교체했다.

- 실제 RTL: Top·Control·Memory·MAC. MAC 소스는 `mac_array`, `dot_product4`, `signed_multiplier8`, `adder_tree4`와 공통 `signed_adder32`다. 기존 공통 `register_en`·`delay_line`을 함께 사용한다.
- 임시 모델: 누산기·후처리만 유지한다. `modeled_modules=["accumulator_postprocess"]`이며 `verification_scope=top_with_behavioral_models`를 유지한다.
- MAC 모델은 Top 컴파일 소스에서 제외하고 파일 자체와 이전 실행 결과는 보존한다. Top RTL·TB·tester·기존 golden 헤더·기대값·비교 마스크·시간 설정은 변경하지 않는다.
- 기존 실행기 테스트의 소스 구성 기대값도 갱신했다. 이후 사용자 요청에 따라 변경한 구성의 컴파일·계층 전개·xsim과 실행기 테스트 12개를 통과했다.

기존 `python project/90_scripts/run.py mlp_top` 명령으로 실행했다. 실제 Control의 입력 공급과 실제 Memory·MAC의 데이터·valid 지연이 연결된 결과를 기존 레이어별 저장값·prediction·최종 버퍼 비교로 확인했다. 누산기·후처리가 모델이므로 `rtl_verified=false`다.
